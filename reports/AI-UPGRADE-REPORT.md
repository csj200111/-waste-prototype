## 0. 이 보고서를 읽기 전에 (3줄 요약)

1. **직전 버전(04-05)** 은 백엔드/AI 서버 양쪽에 **새 방식(2-Stage) 손상 분류 코드와 인프라(`DamageLevel` enum 등) 가 이미 갖춰져 있던 "준비 단계"** 였습니다. 단, 핵심 부품인 손상 분류 모델 파일(`damage.pt`) 이 아직 없었고, 동시에 AI 서버가 기존 1-Stage 방식의 결과(`broken/scratch` 박스) 를 명시적으로 무시하도록 바뀌어 있어서, **실제 운영에서는 사용자에게 손상 정보가 거의 전달되지 않는 상태** 였습니다.
2. **현재 버전(04-19)** 에서는 **학습 완료된 `damage.pt` 파일을 배치** 하여 잠들어 있던 2-Stage 신방식이 깨어났고, **사용자가 다시 손상 정보를 받을 수 있게** 되었습니다.
3. 추가로 운영 사진 테스트 결과를 반영해 **손상 단계 임계값을 0.7 → 0.5 로 완화** 하여, 명백한 파손이 약하게 표시되던 문제를 해결했습니다.

## 1. 어려운 용어 사전 (먼저 읽어주세요)

| 용어 | 쉬운 설명 |
|---|---|
| **AI 모델** | 사진을 보고 답을 내놓는 프로그램. 미리 학습시켜 둔 결과물. |
| **YOLO** | 사진 속 물체의 위치와 종류를 동시에 찾는 대표적인 AI 기술. |
| **Detection (탐지)** | "여기에 의자가 있다" 처럼 위치를 네모 박스로 찾아내는 작업. |
| **Classification (분류)** | "이 사진은 정상이다" 처럼 사진 한 장 전체에 라벨 하나를 붙이는 작업. |
| **클래스 (Class)** | AI가 구분할 수 있는 카테고리. 예: "의자", "TV", "broken". |
| **bbox (바운딩 박스)** | 사진 속 물체를 둘러싼 네모 박스의 좌표. |
| **크롭 (Crop)** | 사진의 일부분만 잘라내는 것. |
| **모델 가중치 (.pt 파일)** | 학습이 끝난 AI의 두뇌에 해당하는 파일. |
| **Confidence (신뢰도)** | AI가 자기 답에 얼마나 확신하는지를 0~1로 표현한 점수. |
| **Threshold (임계값)** | "이 점수 이상일 때만 인정한다" 의 기준선. |
| **1-Stage / 2-Stage** | AI 모델 1개로 처리 / 2개를 줄지어 처리. |
| **Pipeline (파이프라인)** | 여러 작업을 줄지어 처리하는 구조. |
| **Graceful Degradation (우아한 성능 저하)** | 일부 기능이 빠져도 서비스가 멈추지 않게 설계하는 방식. |
| **Enum (이넘)** | 정해진 선택지 목록. 예: 신호등 = {빨강, 노랑, 초록}. |
| **공공 데이터셋** | 정부·공공기관이 무료 공개한 학습용 데이터 모음 (예: AI Hub). |

## 3. 직전 버전(04-05)의 정확한 동작 상태

### 3.1 코드 / 인프라

다음이 04-05 시점에 **이미 갖추어져 있었습니다**:

- `ai-server/app.py` — 2-Stage 파이프라인 코드 (탐지 → 크롭 → 분류) 작성 완료
- `ai-server/split_damage_dataset.py` — 손상 데이터셋 빌드 스크립트
- `ai-server/train_damage_cls.py` — 손상 모델 학습 스크립트
- `backend/.../ai/DamageLevel.java` — 손상 단계 4개 enum (NONE/MINOR/MODERATE/SEVERE), 임계값 **0.7**
- `backend/.../ai/dto/DamageInfo.java` — 손상 정보 DTO
- `AiPredictionService` — 응답에서 `broken/scratch` 박스를 손상 정보로 변환하는 호환 처리 코드

### 3.2 그러나 실제 운영 상태는 "비활성"

`app.py` 의 다음 두 줄이 결정적입니다:

```python
# ai-server/app.py - 04-05 시점
DAMAGE_CLASS_NAMES = {'broken', 'scratch'}
...
for box in result.boxes:
    class_name = detect_model.names[cls_id]
    # 탐지 모델의 broken/scratch 결과는 무시
    if class_name.lower() in DAMAGE_CLASS_NAMES:
        continue                                  # ← 응답에서 제외
```

여기에 **`damage.pt` 파일이 없으므로** `classify_damage()` 함수는 곧장 None 을 반환합니다.

종합하면 04-05 시점에 사용자가 사진을 찍으면:

| 처리 단계 | 결과 |
|---|---|
| ① 탐지 모델로 물건 찾기 | "의자, 신뢰도 0.92" 검출 |
| ② broken/scratch 박스 처리 | **응답에서 제외 (`continue`)** |
| ③ damage.pt 로 크롭 영역 분류 | **damage.pt 없음 → None 반환** |
| ④ 백엔드의 손상 처리 분기 | `damageType` 이 항상 null → **`DamageLevel.NONE`** 으로 응답 |

→ 사용자에게 전달되는 `damage` 필드는 거의 항상 `{ type: null, level: NONE }` 상태였습니다.

### 3.3 왜 이런 과도기 상태가 만들어졌나?

이전 단계(03-16 시점)에는 1-Stage 구방식으로 손상 분류가 동작했지만, **정확도가 낮다는 한계**가 있었습니다 (`ai-upgrade.md` 문서에 명시).

이를 해결하기 위해 04-05 에는 **2-Stage 신방식으로 갈아타는 작업의 절반(코드)** 만 먼저 들어갔고, 나머지 절반(학습된 모델 파일) 은 학습이 끝나는 04-15 까지 기다려야 했습니다.

그 사이 기간에는 손상 정보가 사용자에게 전달되지 않는 **graceful degradation 상태** 가 의도적으로 유지되었습니다 (잘못된 손상 정보를 보내느니 차라리 안 보내는 쪽).

## 4. 현재 버전(04-19)에서 무엇을 바꿨는가

### 변경 1) `damage.pt` 학습 완료 후 배치 (04-15, `697db81`)

학습이 완료된 손상 분류 모델 파일을 `ai-server/model/` 에 추가.

**효과:** 04-05 시점에 잠들어 있던 신방식 코드(`if damage_model is not None`) 가 처음으로 실제 동작하기 시작.

```diff
+ ai-server/model/damage.pt         (신규, 약 9.8 MiB — 학습 완료된 손상 분류 모델)
+ ai-server/model/best_backup.pt    (탐지 모델 백업본, 약 6.1 MiB)
+ ai-server/yolov8s-cls.pt          (분류용 사전학습 가중치, YOLOv8s-cls)
+ ai-server/yolo26n.pt              (학습 보조 파일 — 03-08 cleanup 에서 한 번 제거되었다가 04-15 에 다시 추가된 파일. 정확한 용도는 커밋 메시지에 명시되어 있지 않음)
```

이 변경 한 가지로 사용자 응답 안에 다음이 채워지기 시작합니다:

```json
{
  "predictions": [
    {
      "className": "chair",
      "confidence": 0.92,
      "bbox": {...},
      "damageClass": "broken",          ← 새로 채워짐
      "damageConfidence": 0.78          ← 새로 채워짐
    }
  ],
  "damage": {                            ← 새로 채워짐
    "type": "broken",
    "confidence": 0.78,
    "level": "SEVERE"
  }
}
```

### 변경 2) 손상 판정 임계값 완화: 0.7 → 0.5 (04-15, `5c23897`)

`DamageLevel.java` 의 두 줄 수정:

```diff
  if ("broken".equals(type)) {
-     return confidence >= 0.7 ? SEVERE : MODERATE;
+     return confidence >= 0.5 ? SEVERE : MODERATE;
  }
  if ("scratch".equals(type)) {
-     return confidence >= 0.7 ? MODERATE : MINOR;
+     return confidence >= 0.5 ? MODERATE : MINOR;
  }
```

**왜 바꿨나?**

`damage.pt` 가 활성화된 직후 실제 사용자 사진들을 테스트해 보니:
- 사람 눈으로 봐도 명백히 부서진 물건의 신뢰도가 **0.5~0.7 구간** 에 자주 머물러 SEVERE 로 잡히지 않음
- "심각한 파손인데 MODERATE 로만 분류되어, 나눔 가능 여부가 잘못 판정" 되는 사례 발생

모델 재학습 대신 **임계값 두 줄을 즉시 조정** 하는 빠른 대응을 선택.

## 7. 사용자 입장에서 무엇이 달라졌나?

### 직전 버전(04-05)

- 부서진 의자 사진을 찍어도 → AI 응답: "의자, 신뢰도 0.92"
- 손상 단계는 거의 항상 NONE 으로 표시 (실제로 동작하지 않음)
- 사용자가 직접 보고 나눔/배출을 판단해야 함

### 현재 버전(04-19)

- 부서진 의자 사진 → AI 응답: "의자, 신뢰도 0.92, 손상 단계: SEVERE (심한 손상), 나눔 불가"
- 시스템이 자동으로 "이건 나눔 대신 폐기물 배출" 같은 분기 안내 가능
- 임계값 0.5 적용으로 미묘한 파손도 놓치지 않음

## 9. 결론

이번 업그레이드의 본질은 **"이미 작성되어 있던 신방식 코드를, 학습된 모델 파일을 배치하여 실제로 가동시키고, 운영 데이터에 맞게 미세 조정한 것"** 입니다.

직전 버전(04-05) 이 코드는 다 갖추었지만 **모델 파일이 없어 손상 정보가 비어 있던 "준비 단계"** 였다면, 현재 버전(04-19) 은 그 빈자리를 채워 **사용자가 실제로 손상 단계 정보를 받게 된 "활성 단계"** 입니다.

비유하자면:
> 직전 버전은 **새 자동차의 차체와 엔진룸은 다 만들어 놨지만 엔진(=`damage.pt`) 을 아직 안 끼운 상태**,
> 현재 버전은 **엔진을 끼우고 시동을 건 후, 운전 감각을 보고 액셀의 민감도(=임계값) 를 조정한 상태** 입니다.

핵심 변경은 단 두 가지:
1. **`damage.pt` 한 개 파일 추가** → 잠들어 있던 2-Stage 신방식이 깨어남
2. **임계값 두 줄 수정** → 운영 사진에 맞게 민감도 조정

코드 변경량은 최소이지만, **사용자에게 전달되는 손상 판정 기능이 사실상 무에서 유로 활성화** 되었다는 점에서 체감 효과는 큽니다.

### 다음 단계로 검토할 만한 것

- 임계값 0.5 가 반대로 오탐(정상을 손상으로 잘못 분류) 을 늘리지 않는지 모니터링
- damage.pt 의 클래스별 정확도(precision / recall) 정기 측정
- 임계값을 코드 대신 환경설정 파일로 빼서 재배포 없이 조정 가능하게 변경
- 백엔드의 1-Stage 구방식 호환 코드(broken/scratch 박스 처리) 가 현 운영에서는 사용되지 않으므로, 충분히 검증되면 제거 검토
